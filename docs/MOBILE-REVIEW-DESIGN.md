# P4 移动复习与同步开发方案

2026-10-27 设计基线 e918844；2026-10-30 更新。方案和协议技术验证已完成，A1 独立移动演示页面与实际本地存储已交付，见 [MOBILE-REVIEW-PROTOTYPE.md](MOBILE-REVIEW-PROTOTYPE.md)。**正式设备配对、签名复习包与生产同步尚未实现。** 桌面现有流程与已发布 v0.3.3 保持原样。

## 第一版解决什么问题

先允许用户把一小批到期练习卡带到手机，断网完成回忆并保留作答，回到桌面确认入账。第一版只复习已学过的六类练习卡；不增加新词/新卡，不在手机编辑资料、生成 AI 内容、改变调度或直接读写桌面数据库。

选择独立的轻量 Web/PWA 入口，复用题型、数据契约与现有评分规则。第一条传输链路使用用户主动选择的文件往返，不要求先开发账号、托管学习数据库或让桌面常驻监听网络。文件往返会增加操作步骤，作为可验证的第一阶段；之后在同一协议上加自动传输。

PWA 的 Service Worker 需要 HTTPS 安全上下文，本机 localhost 例外仅适用于开发；手机不能靠打开电脑的普通 HTTP 地址获得同等离线能力。[Service Worker 官方文档](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API)。正式静态站点的域名、部署与手机适配另行交付，本批没有发布站点。

## 目标用户流程

1. 在桌面主动创建设备配对邀请，手机生成自己的设备身份，双方核对确认码后，桌面确认信任该设备。允许在桌面查看并撤销设备。
2. 桌面按当前复习计划签发最多 30 张**已介绍、使用中且到期**的卡，默认有效 24 小时。用户预览范围后导出设备专用复习包；包中包含题面、选项、参考答案/解析及必要的原文快照，不包含 AI 凭据、设置、聊天、其他卡或本机备份路径。
3. 手机核验设备、签名、库与轮次后导入，先作答再展开答案。选择/判断/拼写/填空继续使用相同规则，最终结果仍由桌面重新核对。
4. 点击评分后，先把完整作答及固定操作身份写入本地事务。完成后显示“已在此设备记录，待桌面确认”；同卡在该作答待确认期间不再次排队。没有网络也能继续其他卡。
5. 手机导出作答包，用户在桌面预览处理范围并导入。桌面核验身份、当前基线和实际答案后，逐项事务入账，导出签名回执。失败项目继续待确认；已成功项目重试返回相同结果。
6. 手机核验并导入回执，分别显示“桌面已确认”“存在冲突”“仍待确认”。原作答保留；冲突页同时展示原题、原回答和当前卡片状态，不能自动覆盖或冒充一次成功复习。

独立的移动静态入口与学习资料分离，不把整库预置到站点上。是否部署站点、放在哪里及后续服务成本，在对应开发批次明确；现有桌面离线使用不依赖这些服务。

## 本批协议原型

`shared/mobile-review-contract.mjs` 是无 Node、Vue、网络和数据库依赖的 ES 模块，提供严格格式校验、可重复的字段序列化、只读基线比对和待确认队列转换。当前没有被生产页面、preload 或 IPC 引用，不会自行评分或同步。

| 数据 | 关键字段与约束 |
| --- | --- |
| operation | v、operationId、libraryId、libraryEpoch、deviceId、batchId、cardId、expectedRevision、contentKey、scheduler、response、ratingScale、rating、answeredAt、sequence |
| ticket | 库/轮次/设备/批次身份、issuedAt/expiresAt，以及最多 30 个签发卡片的版本/内容摘要/调度身份；不是完整展示用复习包 |
| scheduler | legacy-card 的版本 1，或 fsrs-card 的库版本 5.4.2、参数摘要及内容轮次；三档和四档不能混用 |
| outbox | 库/设备身份、单调 nextSequence、最多 200 个完整操作及可空 confirmation；不存会因重启卡住的 sending 状态 |
| receipt | 原规范化操作、applied/conflict、冲突码，以及成功时桌面确认的 reviewedAt/due；不匹配的回执不能清除待确认项 |

UUID 均采用小写标准形式，内容/参数摘要为 64 位十六进制，时间为带毫秒的 UTC ISO 字符串，输入最多 10000 字符。未知字段、稀疏数组、重复卡、无效日期、超长批次/队列或非法评分拒绝，不静默截断。原始回答和手机时间保留，不把大小写/空白规范化后的值替代原数据。

`operationKey` 是原型 v1 按固定字段顺序生成的 JSON 字符串，用于比较请求内容，**不是签名、哈希或权限凭据**。未来签名封装对规范化字节另加类型域前缀，例如 `CETWordKeeper/review-op/v1\0`；ticket、receipt、配对请求使用不同前缀。不能直接对属性顺序任意的原始 JSON 签名，也不能把未知字段剔除后当成已签名的原请求。

`classify` 只返回 `base-match`、`conflict` 或 `duplicate`。`base-match` 只证明版本等字段吻合；调用方仍须验证签名、权限和真实答案，不能把它当作允许写库。device、ticket、previous 等参数必须由可信适配层从本地登记或验签结果提供，不能从客户端同名字段直接透传。

## 调度、时间与冲突规则

桌面是首版唯一调度写入者。移动端只保存作答意图；不自行写 due、correct、FSRS 记忆状态、复习额度或实际完成统计。客户端注入这些字段会被协议拒绝。

新作答入账前逐项检查：设备仍有效、库与恢复轮次匹配、批次归属/有效期、卡片在签发范围内、版本与内容摘要一致、调度版本/参数/轮次一致、当前使用中且到期、已学过。改题、暂停/归档、另端评分或调度切换均明确冲突，保留原记录，不用最后写入者覆盖。

手机 `answeredAt` 仅作原始作答时间审计；首版由桌面接收确认时间计算实际间隔和统计日期，不回写到过去。手机时钟偏差仅提示，不能用未来时间加速或倒退调度。此策略牺牲了延迟传回时的精确作答时刻，因此首版批次限 24 小时，不宣称离线记录已用于精确 FSRS 时间回放。桌面时间早于批次签发时间时也阻止新入账。

已入账操作重试：先检查当前设备和库轮次，再查原回执；即使批次过期或已清理也不重复评分。相同身份却改变回答/评分等内容，返回 operation-reused；duplicate 的内层回执可能是冲突，不能把所有 duplicate 都显示为学习成功。未入账的过期批次返回冲突，手机仍保留原作答。

恢复数据库必须产生新的外部 libraryEpoch 并撤销旧配对，不能从旧备份恢复出仍有效的设备凭据。libraryId 是用户库专属随机身份，不使用所有人相同的分发库摘要。旧手机仍可保留/导出记录，但不能把旧轮次的作答自动写进新状态。

## 配对、验签与撤销设计

采用每端独立的 ECDSA P-256 密钥对，SHA-256 签名，WebCrypto 的 P1363 签名格式；私钥在手机端以不可导出 CryptoKey 保存，桌面仅登记设备公钥。公钥机制和签名编码依据 [WebCrypto sign 文档](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/sign)。本批只验证签名基元互通，未实现配对或安全协议适配层。

配对邀请包含桌面公钥指纹、库/轮次、随机挑战和五分钟有效期。手机生成设备密钥后，签署绑定邀请与自身公钥的请求。桌面验证挑战未使用/未过期、核对双方确认码，再由用户确认设备名称及公钥身份；不能仅凭收到文件就自动授权。挑战一次消费，桌面发出绑定设备的确认。手机必须核对桌面身份后才能信任复习包和回执。

撤销在桌面权威登记中立即生效，拒绝新提交和旧回执查询；不回滚已经确认的学习，不承诺远程删除离线设备上的已导入资料。重新配对使用新设备身份。恢复数据库后的新轮次/撤销状态应在数据库恢复事务之外持久化并由恢复流程管理，防止旧备份使设备信任复活；A2 需具体实现和故障测试。

完整复习包、作答包、回执都必须验签和限制总字节后再传给本模块。复习包内容摘要需绑定题面、答案、解析与出处，不能只验证 ticket 而展示未经绑定的题目。包格式、私钥保存/恢复、挑战存储与权限白名单属于后续 A2，不以当前只读比对替代认证。

## 持久化与事务接入

移动端采用 IndexedDB，在同一 readwrite 事务中读取最新队列、分配序号、保存操作。等 transaction complete 才提示本地记录成功，不能在单个 put success 时提前提示，也不能在事务中等待网络。浏览器对突发断电的持久性保证存在差异，不能把正常重启测试表述为任何情况下绝不丢失。[IndexedDB 事务说明](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction)。

重启后恢复 pending，无需判断上次网络请求是否发出；重传完整相同身份和内容。确认回执与原记录同事务落库；不匹配/变造回执使事务中止。并发标签页也从数据库读当前序号，不能各用独立内存计数器。队列达到 200 条时停止新增并说明处理方法，后续界面须提供导出副本、检查确认及显式清理已确认项，禁止自动删除冲突腾位置。

桌面后续新增 mobile_device、mobile_batch、mobile_operation、mobile_conflict 等增量数据结构，并建立 `(libraryEpoch, deviceId, operationId)` 与设备内 sequence 唯一约束。服务端不能要求按手机时间排序，也不能因一个缺失序号永久阻止后续独立操作；相同序号绑定不同操作应拒绝。

手机 operationId 与现有 practice_attempt 的全局主键隔离：适配层为每个首次有效操作分配独立 localAttemptId 并持久化映射，不能直接复用客户端 UUID 造成与原生桌面评分碰撞。入账时在同一事务保存实际评分、typed 核对、FSRS/原调度事件、额度记录和 mobile_operation 回执；重复请求由回执返回，不再评分。

现有 practice.rate 自己开启 persistTransaction，不能在外层再次 BEGIN。A2 应先提取内部“验证/计算/事务内写入”服务，保留原 API 行为，再接联合提交；禁止“先调用评分，稍后另存回执”造成崩溃窗口。逐操作原子提交允许一批部分成功，返回各自稳定回执；SQL/写盘故障不虚报成功。当前隔离演练直接调用旧评分接口验证兼容，不代表这个联合事务适配已经完成。

## A0 验证记录与范围

运行 `npm run test:mobile-contract`：

- 28 项协议/队列与隔离评分演练：载荷限制、序号、原输入、重传/回执、版本/内容/参数冲突、批次到期、恢复轮次、撤销状态、时钟偏差、真实旧调度/FSRS 四档、错误拼写高分拒绝和落盘回滚。

浏览器测试使用专用隐藏窗口和拥有标记的临时用户目录，服务只绑定 127.0.0.1；结束关闭并清理。没有访问真实用户库、调用模型、启动生产监听服务、部署站点、修改生产评分/迁移或生成安装包。IndexedDB 与签名代码目前是测试原型，不等于已交付手机端持久化或配对。v0.3.3 发行标签和附件不变。
